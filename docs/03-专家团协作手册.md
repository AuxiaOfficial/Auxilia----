# Auxilia 专家团协作手册

> 这份文档解决一个问题：**怎么让 AI 在几十次对话之后，做出的东西还是同一个产品。**

---

## 1. 先说清楚：AI 做大项目真正会死在哪

不是模型不够聪明。是这三件事：

| 死因 | 表现 | 后果 |
|---|---|---|
| **上下文衰减** | 第 15 次对话时，AI 已经忘了第 3 次定下的"TaskLine 只做参考、不自动执行" | 产品哲学被一点点侵蚀，最后变成一个普通番茄钟 |
| **验收缺位** | AI 说"已完成"，你没验，继续往下做 | 地基裂缝被上层建筑盖住，两周后发现要重写 |
| **角色混淆** | 同一个 AI 会话里，它一会儿当设计师一会儿当工程师，审美和工程各妥协一半 | 界面既要极简又要功能齐全，结果两边都不像 |

专家团存在的意义**不是扮演角色好玩**，而是用三个机制堵住这三个洞：
1. **交接物写文件**（抗上下文衰减）
2. **每阶段硬验收**（抗验收缺位）
3. **一次会话只当一个角色**（抗角色混淆）

## 2. 五个角色

### 🏛 R1 · 产品架构师（Architect）

| 项 | 内容 |
|---|---|
| **一句话** | 产品哲学的守门人，技术决策的最终裁定者 |
| **负责** | 维护 `docs/01-产品规格书.md`、`docs/02-技术架构.md`；冻结模块间接口；裁决"这个需求该不该做" |
| **输入** | 你的想法、开发中暴露的矛盾 |
| **产出** | 更新后的规格书条目、接口契约、技术决策记录 |
| **禁止** | ❌ 写业务代码 ❌ 改视觉细节 ❌ 在没有你确认时改产品哲学 |
| **何时叫他** | ① 项目开始（一次）② 遇到"做不下去了，要不要砍功能"③ 两个模块接口对不上 ④ 阶段验收后需要更新规格 |

> **这个角色只需要出场 3-5 次。** 但现在这几份文档就是他第一次出场的成果。

### 🎨 R2 · 视觉设计师（Designer）

| 项 | 内容 |
|---|---|
| **一句话** | 定死"纯黑极简苹果风"到底长什么样，之后所有人照着做 |
| **负责** | `src/styles/tokens.css`（唯一颜色/间距/圆角/动效来源）、组件视觉规范、关键页面的静态视觉稿 |
| **输入** | 规格书第 2 章（设计哲学）、参考图（Grok 界面截图、App Store 风格） |
| **产出** | tokens.css + 一份 `docs/04-视觉规范.md`（可选）+ 3-5 个核心组件的样式基准 |
| **禁止** | ❌ 写业务逻辑 ❌ 引 UI 组件库 ❌ 发明规格书外的交互 |
| **何时叫他** | ① P1 脚手架之后、写任何业务组件之前（**必须**）② 某个页面"做出来不好看"③ 徽章/装饰墙这类需要插画感的模块 |

**为什么设计师必须排在前面**：如果他后到，前端已经用 5 种不同灰度写完了 30 个组件，改起来比重写还贵。

### ⚛️ R3 · 前端工程师（FE）

| 项 | 内容 |
|---|---|
| **一句话** | React 组件、交互、动效、状态管理 |
| **负责** | `src/` 下除 Rust 调用外的全部 |
| **输入** | P0 宪法 + 当期 prompt + tokens.css + 已完成模块清单 |
| **产出** | 可运行代码 + 自测截图/说明 |
| **禁止** | ❌ 改 `src-tauri/` ❌ 新增依赖（需 Architect 同意）❌ 绕过 tokens.css 硬编码颜色 |
| **何时叫他** | P2 ~ P9 的绝大部分工作 |

### 🦀 R4 · 桌面工程师（Desktop）

| 项 | 内容 |
|---|---|
| **一句话** | Rust 侧：计时引擎、窗口管理、系统集成、SQLite |
| **负责** | `src-tauri/`、`migrations/`、IPC 命令、托盘、快捷键、自启 |
| **输入** | 架构文档第 5/6/7 章 + 接口清单 |
| **产出** | 可运行的 `cargo build` + IPC 接口文档 |
| **禁止** | ❌ 写 React 组件 ❌ 改前端样式 |
| **何时叫他** | P1（脚手架）、P2（数据层）、P6（执行引擎与系统集成）、P9（打包）为主；其他阶段偶尔补 IPC |

### ✅ R5 · 验收官（QA）

| 项 | 内容 |
|---|---|
| **一句话** | 唯一有权说"这个阶段没完成"的人 |
| **负责** | 按 `prompts/验收清单.md` 逐条实测；记录失败项；写回状态板 |
| **输入** | 当期完成的代码 + 验收清单 + 边界条件表（规格书第 6 章） |
| **产出** | 通过/不通过清单，失败项必须带**复现步骤** |
| **禁止** | ❌ 顺手改代码（只报告，不改）❌ 因为"看起来没问题"就跳过 |
| **何时叫他** | **每个里程碑结束时，无条件** |

> QA 不改代码这个限制很重要。一旦 QA 自己动手，它就会倾向于"我想的都对"，失去对抗性。

## 3. 协作时序

```
P0  项目宪法 ──────────────────────────────── [已有]
 │
P1  脚手架 + 设计系统
 │   R4 → 跑通 dev 空壳
 │   R2 → tokens.css + 组件规范        ← 设计先行
 │   R5 → 验：能启动、token 生效、hotkey 通
 │
P2  数据层 + 任务模型
 │   R4 → migrations + IPC
 │   R3 → 任务池列表读写
 │   R5 → 验：CRUD 全通、软删除正确
 │
P3  主界面三栏
 │   R3 → Sidebar / CenterStage / TimelinePanel 骨架
 │   R5 → 验：三栏布局 + 空状态
 │
P4  新建任务 + 阻尼滚轮  ★ 手感关键
 │   R3 → 五组属性 + 滚轮物理
 │   R5 → 验：手感 5 条（架构文档 6.2）
 │
P5  TaskLine
 │   R3 → 时间轴 + 拖放 + 多 TL
 │   R5 → 验：点击才执行、拖放落位准确
 │
P6  执行引擎 + 系统集成  ★ 最难
 │   R4 → engine.rs + 四个窗口 + 托盘 + 自启
 │   R3 → Focus 页 + MiniBar + FloatCard + FinishFlow
 │   R5 → 验：睡眠恢复、杀进程恢复、scheduled 冲突
 │
P7  结束流程 + 复盘系统
 │   R3 → 三问递进 / 复盘向导 / 归档导出
 │   R4 → 统计聚合 SQL
 │   R5 → 验：三问链路 + 归档正确
 │
P8  成就系统 + 装饰墙
 │   R2 → 热力图/图表/徽章视觉
 │   R3 → SVG 图表 / 徽章求值触发 / 商店
 │   R5 → 验：数据正确 + 无 NaN + 无彩色污染
 │
P9  导入导出 + 引导 + 发布
 │   R3/R4 → 导出码 / 批量管理 / 设置 / 引导
 │   R2 → 应用图标
 │   R5 → 验：6 条终验 + 性能指标 + 安装包
```

### 3.1 串行是默认，并行是例外

**默认全程串行。** 因为：
- 上下文成本最低（每次只需带 P0 + 当期 prompt）
- 出错时归因简单

**只有这几种情况值得并行**（且必须在**两个独立会话**里做）：

| 可并行的组合 | 前提 |
|---|---|
| P8 的「成就图表」 ⟷ P9 的「导出码」 | 两者不碰同一文件 |
| P7 的「复盘向导」 ⟷ P6 的「托盘菜单」 | 前端页 vs Rust 侧 |
| 装饰墙拖拽 ⟷ 热力图 | 都是纯前端独立组件 |

**并行的铁律**：开工前先让 Architect 写下一句话接口约定（"成就页只读 `getStats(range)`，不写库"），两个会话各自照做。**没有接口约定就不要并行**，否则合并时是灾难。

### 3.2 每个阶段开一个新会话

不要在一个会话里从 P1 干到 P8。理由：
- 上下文会爆，早期约束被挤出窗口
- 出错时无法二分定位

**每次开新会话的标准动作**（30 秒）：
1. 粘 P0 项目宪法
2. 粘当期 prompt
3. 粘 `STATE.md` 当前进度（见第 5 章）
4. 加一句"先复述你的实现计划，我确认后再写代码"

## 4. 每次对话的开场模板

### 4.1 标准开发会话

```text
【角色】你是 Auxilia 项目的 {前端工程师 | 桌面工程师 | 视觉设计师}。
只做这个角色的职责，不要越界到其他角色。

【必读】下面三段内容优先级从高到低，冲突时以高优先为准：
1. 项目宪法（P0）
2. 本期任务说明
3. 当前项目状态

===== 1. 项目宪法 =====
{P0-项目宪法.md 全文}

===== 2. 本期任务 =====
{P4-新建任务与阻尼滚轮.md 全文}

===== 3. 当前项目状态 =====
{STATE.md 全文}

【工作要求】
1. 先输出你的实现计划（分成几个文件、每个文件负责什么、有哪些技术风险），
   等我确认后再写代码。不要跳过这一步。
2. 如果需要修改宪法或架构文档中的约定，先停下来告诉我，不要自行决定。
3. 代码写完后，列出你自测了什么、没测什么。
```

### 4.2 验收会话（R5）

```text
【角色】你是 Auxilia 项目的验收官。你的唯一职责是找出问题，不是修问题。

【依据】
1. 验收清单：{prompts/验收清单.md 中本期部分}
2. 边界条件：{01-产品规格书.md 第 6 章}
3. 技术约束：{02-技术架构.md 第 6 章}

【被测代码】{说明本期新增/修改了哪些文件}

【要求】
1. 逐条对照清单，明确给出 通过 / 不通过 / 无法验证。
2. 不通过的必须写：期望行为 → 实际行为 → 复现步骤 → 严重级别（阻断/严重/轻微）。
3. 不要因为"代码看起来对"就判定通过，必须给出你如何验证的。
4. 不要修改任何文件。
```

### 4.3 卡住时的升级会话（R1）

```text
【角色】你是 Auxilia 的产品架构师。

【现状】{描述卡住的地方，粘贴报错/失败项}
【已尝试】{列 2-3 种方案及失败原因}

【要求】
1. 判断这是实现问题还是需求问题。如果是需求问题，直接说"这个需求要砍/要改"。
2. 给出 2 个可选路径，各自代价是什么（时间/复杂度/对产品哲学的损伤）。
3. 推荐一个，并说明如果选它，需要同步修改哪几份文档。
```

## 5. 状态板 `STATE.md`（整个协作机制的枢纽）

放在项目根目录。**它是 AI 之间唯一的记忆载体**，每次开新会话都要贴。

```markdown
# Auxilia 项目状态

## 当前阶段
P4 新建任务与阻尼滚轮 —— 进行中

## 已完成（可依赖，不要重写）
- [P1] Tauri 2 脚手架跑通，`pnpm tauri dev` 正常
- [P1] tokens.css 已定稿（黑底 #000 / 文字 #FAFAFA / 面板 #0A0A0A / 强调 #E8E8E8 / 警示 #FFB84D）
- [P1] 全局快捷键 Shift+Space 可用，唤起隐藏正常
- [P2] 数据库 13 张表建好，migrations 可重复执行
- [P2] 任务池 CRUD 通，软删除生效
- [P3] 三栏布局骨架 + 空状态

## 进行中
- [P4] DurationWheel 组件：物理内核已写，吸附收敛有抖动，待调参

## 未开始
- P5 TaskLine / P6 执行引擎 / P7 成就复盘 / P8 导出打磨

## 已确认的关键决策（不得推翻）
- 单任务串行，全局只允许一个 running（规格 FR-E1）
- TaskLine 不驱动执行，点击才跑（规格 FR-D5）
- 计时用时间戳差，不用累加（架构 6.1）
- 暂停时间不计入专注时长与 coin（规格 5.4）
- Windows 无顶栏，用贴顶迷你浮条替代（规格 5.1）
- 不引入 UI 组件库与图表库（架构 1）

## 已知坑
- WebView2 隐藏窗口定时器会被节流到 1s，别改成 setInterval 累加
- Shift+Space 可能被输入法占用，需检测注册返回值
```

**维护规则**：每完成一个条目就往「已完成」挪，并更新「当前阶段」。这是你唯一必须手动做的事。

---

## 6. 十分钟成本的三条纪律

1. **不要在一次会话里跨阶段。** 跨了就会开始糊。
2. **每个里程碑结束必须跑一次 QA 会话。** 哪怕只花 5 分钟，哪怕你觉得"肯定没问题"。AI 最容易在"觉得自己做完了"的时候留下洞。
3. **改了接口就改文档。** 文档落后于代码的那天，专家团就开始失效了。

## 7. 如果你用 WorkBuddy 的专家中心

上面 5 个角色可以用两种方式落地：

| 方式 | 适用 | 做法 |
|---|---|---|
| **同一会话切换角色提示** | 大多数情况 | 每次开新对话，粘对应角色模板（第 4 章）。最简单，上下文最干净 |
| **挂一个专家 / 专家团** | 想要角色常驻、不想每次粘模板 | 在左侧「专家」里选产品/设计/前端相关专家作为常驻角色，再把 P0 宪法固定在对话开头 |

对单人项目，**推荐第一种**。角色切换的收益来自"约束"，而不是"人设"——一份写得足够硬的 P0 宪法，比一个泛泛的"资深工程师"人设有用得多。
